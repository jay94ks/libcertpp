# Contributing to libcertpp

[한국어](CONTRIB.ko.md)

Thank you for improving `libcertpp`. This guide defines the contribution
workflow for both people and AI coding agents. The same correctness and
documentation standards apply to both; the two audience-specific sections
below describe how each should prepare work for review.

## Start here

Before changing the library, use the repository documentation according to
its purpose:

- [`docs/README.md`](docs/README.md) is the documentation map and explains
  which document owns each kind of information.
- [`docs/CONCEPTS.md`](docs/CONCEPTS.md) describes the current module
  boundaries and public surface.
- [`docs/RULES.md`](docs/RULES.md) defines the code,
  naming, comment, and test conventions.
- [`docs/BUILDING.md`](docs/BUILDING.md) contains the complete build and test
  commands.
- [`specs/README.md`](specs/README.md) is for callers using the library. It is
  useful when a change affects public usage, but it is not the contributor
  guide.
- [`SECURITY.md`](SECURITY.md) defines responsible vulnerability reporting.

AI coding agents must also read [`AGENTS.md`](AGENTS.md) and follow the
[agent-specific workflow](CONTRIB.md#for-ai-coding-agents) below.

## Shared contribution workflow

1. **Establish the contract.** Read the public header, implementation, tests,
   and the relevant architecture or specification section before changing
   behavior. Existing headers are the source of truth for the public API.
2. **Keep the change coherent.** Update declarations, definitions, tests,
   examples, and documentation together. Avoid unrelated cleanup in the same
   change.
3. **Validate independently.** A round trip through this library alone is not
   evidence of interoperability. Cryptographic and encoding work needs a
   published vector, an established second implementation, or a real
   third-party artifact, plus negative cases where applicable.
4. **Run proportionate checks.** Build and run the affected tests. Broaden to
   the full suite when shared code, public headers, build configuration, or
   cross-module behavior changes.
5. **Make the result reviewable.** Explain the user-visible behavior, the
   reason for the change, the evidence used to validate it, and any remaining
   limitation.

## For human contributors

- Start with a focused branch or patch whose purpose can be stated in one
  sentence. For a new public API or cryptographic primitive, describe the use
  case and interface shape before expanding the implementation.
- Build the repository once before editing so environmental failures are
  distinguishable from regressions introduced by the change.
- Include regression coverage for a bug fix and contract-level coverage for a
  feature. Prefer externally sourced vectors over values generated by the code
  under test.
- In a pull request, identify the affected module, any API or ABI impact, the
  exact validation commands run, and the source of interoperability vectors or
  fixtures.
- Keep review commits understandable. Generated output may accompany the
  source that produces it, but the generator or source document must remain
  the authoritative copy.

## For AI coding agents

- Treat `AGENTS.md` and this section as required instructions. Read only the
  task-relevant longer documents after consulting the map in `docs/README.md`.
- Inspect the worktree before editing. Preserve changes already present unless
  the task explicitly asks to alter them, and do not assume that uncommitted
  work belongs to the agent.
- Verify names, signatures, file layout, and nearby conventions from the tree;
  do not invent an API from memory. Search sibling code before introducing a
  new pattern.
- Make the smallest complete change that satisfies the requested behavior.
  Do not broaden scope into opportunistic refactoring or dependency changes.
- Run the relevant checks and report exactly what ran. Never describe a check
  as passing when it was skipped, unavailable, or only inferred from another
  result.
- Update the English source document first and its Korean counterpart in the
  same change. Check relative links and keep language-local links within the
  same language.
- At handoff, summarize the behavior changed, the files or documentation areas
  affected, the validation performed, and any material risk or unresolved
  limitation.

## Requirements by change type

| Change | Required companion work |
| --- | --- |
| Public API | Update the public header and its Javadoc, the matching implementation where needed, `include/certpp.hpp` for a new public header, tests, and caller-facing specs or examples. |
| Cryptography or wire encoding | Use independent known-answer/interoperability evidence and add malformed-input or negative checks. Record security or compatibility limits explicitly. |
| Internal implementation | Preserve the public contract and test through the public surface unless the unit cannot be reached that way. Follow the private-header rules in the coding conventions. |
| Build or installation | Update `docs/BUILDING.md` and `docs/BUILDING.ko.md`, and verify the affected configuration. |
| Documentation | Change the English source and Korean translation together; follow the ownership map in `docs/README.md`. |
| New public type | Add a compiled example under `examples/wiki/` before regenerating the wiki reference. |

## Documentation rules

English documents are authoritative and maintained reader-facing documentation
has a Korean translation beside it named `<name>.ko.md`. The operational
`AGENTS.md` and `CLAUDE.md` entrypoints are exceptions. The counterpart link is
the only content between the level-one heading and the opening paragraph.
Cross-document links stay in the same language whenever a translation exists.

Both `docs/` and `specs/` are maintained documentation. Code changes must audit
both trees: maintainer-facing facts belong in `docs/`, while caller-facing API
tasks and hazards belong in `specs/`. When a public API changes, update every
affected page in the same contribution.

Put information in the surface that owns it:

- current design and module boundaries in `docs/CONCEPTS.md`;
- coding rules in `docs/RULES.md`;
- build and test mechanics in `docs/BUILDING.md`;
- pending requested work in `docs/PLANS.md`;
- historical reasoning and completed investigations in `docs/HISTORY.md`;
- caller tasks, recipes, and misuse hazards in `specs/`;
- executable walkthroughs and wiki examples in `examples/`.

Keep the files at the root of `docs/` as high-level entry points. Group related
details in topical subdirectories instead of creating a file for every small
section. Use short, stable filenames; when a page moves, remove the old file,
update both language indexes, and replace every repository link with the new
page or exact section. Give each fact one owning page and link to it from
summaries rather than maintaining duplicate explanations.

The Markdown files under `examples/wiki/snippets/` are generated by
`tools/exsplit.py`; do not translate or hand-edit them. Wiki API pages are
generated from header Javadocs and compiled examples. See
[`examples/wiki/README.md`](examples/wiki/README.md) for the publication
workflow.

## Building and testing

The usual debug validation is:

```sh
cmake -S . -B build
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
```

Use the existing build directory when it is configured appropriately. See
[`docs/BUILDING.md`](docs/BUILDING.md) for shared/static builds, examples, feature
switches, installation checks, and AddressSanitizer.

## Review checklist

- The change has one clear purpose and preserves unrelated work.
- New behavior is covered by a meaningful test or independently validated
  artifact.
- Error paths and malformed inputs are covered where they affect the contract.
- Public declarations and doc comments match the implementation.
- English and Korean documentation remain paired and equivalent.
- The relevant build and test commands completed successfully and are reported
  accurately.
